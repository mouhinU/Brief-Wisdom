## 第三轮：逐 Token 真流式改造（2026-11-10）

### 一、框架依据

阅读 `spring-ai-openai:2.0.0` 源码（`OpenAiChatModel.internalStream`）确认：

- `call()` 与 `stream()` **都不在模型层执行工具**（无 `executeToolCalls` 调用），工具循环必须由调用方实现，这也是原手动循环存在的原因。
- `internalStream` 用 `bufferUntil` 只在「本轮出现过 tool_call 分片」时才缓冲聚合；非工具轮的每个内容分片各自成一条 `ChatResponse` 下发。因此把工具循环整体换成 `stream()`，即可同时拿到「聚合后的工具调用」与「逐 Token 的最终答案」。

### 二、代码改动

`brief-wisdom-ai/.../ai/service/AiAgentService.java`：

1. 新增常量 `MAX_TOOL_ROUNDS = 5`（替换原方法内的魔法值 `5`）。
2. `chatStreamWithSession` 的工具分支：删除 `chatModel.call()` + `while` 循环 + `Flux.just(response)`，改为调用 `streamToolRound(...)`，并在 `doOnComplete` 记录耗时、触发 `notifyUser(message_added)`，`onErrorMap` 复用 `translateApiError`。
3. 新增 `static Flux<String> streamToolRound(...)`：每轮 `chatModel.stream(prompt)`，`concatMap` 中遇到带 `toolCalls` 的输出则记录待执行消息、不下发文本；否则把文本分片直接下发。轮末用 `Flux.defer` 决定：无工具调用即结束（首轮既无文本又无工具调用则抛 `AIException("AI 模型返回为空")`），有则追加工具调用消息与 `ToolResponseMessage` 后递归下一轮。
4. 新增 `private static executeToolCalls(...)`：原循环内的工具匹配、执行、异常兜底逻辑原样抽出。
5. 两个方法不依赖实例状态，故声明为 `static`（`streamToolRound` 包级可见），便于同包测试直接驱动。
6. 「无工具」分支（Usage 捕获 + 服务端落库）保持原样未动。

新增测试 `brief-wisdom-ai/src/test/java/.../AiAgentServiceStreamToolRoundTest.java`：用脚本化的 `ChatModel` 桩验证 3 个分片逐条下发、工具轮执行一次且第二轮请求含工具结果消息、首轮空响应抛 `AIException`。

### 三、行为变化（需知悉）

1. **输出过滤**：原工具路径先 `filterOutput(全文)` 再整段下发；流式改造后分片无法整体正则替换（逐 chunk 过滤会截断敏感串），因此明文分片直接透传，`filterOutput` 仅作用于「无工具」路径服务端落库的副本。这是唯一的对外可见行为变化。
2. **Usage / 服务端落库**：工具路径原本就不落库（前端 `/message/save` 保存），本轮保持一致。由于 `hasTools` 恒为 true，带 Usage 捕获的「无工具」分支仍是不可达代码，真实 Token/Cost 未打通 —— 该项已在「第四轮」解决。
3. 同步接口 `chatWithSession` 未改动；它同样依赖工具回调，但本就没有工具执行循环，属另一个既有问题，本轮未处理。

## 第四轮：工具路径 Usage 落库 + CI JDK 对齐（2026-11-10）

### 一、代码改动

`brief-wisdom-ai/.../ai/service/AiAgentService.java`：

1. 抽出私有方法 `persistStreamedAssistantMessage(sessionId, userId, model, fullResponse, usage)`，内容为原「无工具」分支 `doOnComplete` 里的落库逻辑（`filterOutput` → 真实 Usage 或估算 Token/Cost → 保存 `ChatMessage` → 刷新会话 `message_count`），逐字搬移，无行为变化。
2. 「无工具」分支改为调用该方法，消除了两条流式路径的重复代码。
3. `streamToolRound` 新增 6 参重载，多传入 `AtomicReference<Usage> usageHolder`；原 5 参签名保留为委托重载，既有单测无需改动。方法内用局部 `roundUsage` 捕获本轮最后一个带用量的 chunk，轮次结束时经 `accumulateUsage()` 跨轮累加进 holder。
4. 新增 `accumulateUsage` / `nullableTokens`：每轮工具调用都是一次独立计费的模型请求，因此按轮求和（`DefaultUsage`）才是整段回复的真实消耗；只取末轮会漏掉前几轮的 completion token。
5. 工具分支的 `doOnComplete` 增加一次 `persistStreamedAssistantMessage(...)` 调用，与 `notifyUser(message_added)` 并存。

**幂等性**：服务端落库后前端仍会调 `POST /api/ai/message/save`，`saveStreamedMessage` 的幂等检查（末条 assistant 消息内容相同则跳过，仅在服务端存的是估算值时补更新）保证不产生重复行；会话标题在流式开始保存用户消息时已由服务端设置（`chatStreamWithSession` 内），不依赖前端兜底，故无回归。

**已知取舍**：流式分片下发前不过滤，落库副本经过 `filterOutput`；两者内容不一致时（命中敏感正则）幂等检查失败，前端会再存一条原始文本。此为「无工具」路径既有行为，本轮未改变，若需收紧应在前端保存时改用 sessionId + 消息序号对账。

新增测试：`AiAgentServiceStreamToolRoundTest#accumulatesUsageAcrossToolRounds` 用带 `ChatResponseMetadata.usage(...)` 的脚本分片验证两轮用量累加为 prompt 300 / completion 35 / total 335。
